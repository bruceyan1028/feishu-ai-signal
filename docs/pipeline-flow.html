0. 总览：八个阶段、两个进程、一张飞书表作为中间存储

采集（python -m src.main）与日报（python -m src.daily）是两个独立进程，中间靠飞书「信号条目表」持久化。所有抓取器都只负责产出带 published_raw 的原始条目，时间窗、关键词、去重全部集中在一个统一漏斗 process.process_and_clean 里。

3. 网页（Scrape）抓取链路 + 网站日期字段识别（scrape.py）

11. 读图时容易误解的地方

  • 两道时间窗是串联的：采集端按源配置放行（默认 168h，纯日期 +24h），日报端再过一次 min(168h, 源窗)，且基准是日报运行时刻。
  • 跨源去重不在采集端：同一事件多个源、URL 不同的条目会并存在飞书表里，只在生成日报时被 collapse_for_brief 折叠，折叠掉的成员进入详情页"事件聚合"。
  • 缺日期即丢弃：任何链路都不会用采集时间冒充发布时间；未来 2 天以上的日期也当作无日期。
  • Scrape 的主截断在列表页：先排序（有日期优先、时间倒序）再取 8 条，所以 max_articles 太小会遮住三周内的稿；tools/date_pipeline_report.py 盘点时临时抬到 60。
  • arXiv 有两套计数：MAX_ARXIV_ITEMS=10 在采集端按 source_id/URL 截一次、日报候选池再限一次；DAILY_MAX_PAPERS=4 却按「来源类型=论文」判，判据不同。
  • 质量分主导最终排序：普通文章 quality_score 恒 0，论文/社媒 20-100，第一排序键会把后者整体顶到前面，impact 只在同质量分组内起作用。
  • 被过滤条目不留正文：只有 output/health/ 里的计数；要看被丢内容要跑 tools/recall_audit.py 或 tools/ab_pipeline.py。
  • config_store / seed_default.json 未接入线上：main.py 直连飞书读配置，改 seed 文件不会影响采集，只影响 tools/ 与 bootstrap --seed。
  • RSS 抓取串行且 404 也会重试满 4 次：raise_for_status() 抛出的 HTTPError 是 RequestException 子类，会进入重试循环。
  • Social 默认不跑：python -m src.main 默认只跑 RSS/Scrape/Media；Podcast 与 Social 各有独立 workflow。
